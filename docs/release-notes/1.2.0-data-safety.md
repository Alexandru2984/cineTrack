# Play data safety — 1.2.0

The 1.2.0 store note flagged that encryption changes what the data-safety form
should say about messages. This is the evidence for filling it, taken from the
code and from the policy already published at
`https://vazute.micutu.com/privacy` — the two must agree, because Play compares
them and a mismatch is a policy violation regardless of which one is right.

**This is not legal advice.** Every row below cites what the service actually
does. Where Play's question turns on a judgment rather than a fact, it says so
instead of answering.

## The message answer, which is the one that changed

**Do not declare messages as end-to-end encrypted without qualification.** That
is not what the service does.

Message text is stored in readable form until *both* accounts have set up
encryption. Only after that does Văzute store ciphertext it cannot read. The
privacy policy already states this exactly (`data9`), and the code allows both
forms — `SendMessageRequest` has a `Plaintext` variant for "conversations where
somebody has not published keys yet".

In production today, all messages are plaintext. Nobody has completed
encryption setup:

```
plaintext | encrypted | total
        2 |         0 |     2
```

So the honest declaration is that **Other in-app messages** are collected, with
the qualifier that they become unreadable to the service once both participants
enable encryption. Claiming blanket E2EE would be false for every conversation
that exists right now.

The same care applies to moderation. A reported *plaintext* message is copied
into the safety report by the service. A reported *encrypted* message is
disclosed **by the reporter**, together with the key proving what the sender
wrote — the service cannot produce it alone.

## Security practices

| Play asks | Answer | Evidence |
| --- | --- | --- |
| Is all user data encrypted in transit? | **Yes** | HTTPS only; `strict-transport-security: max-age=31536000; includeSubDomains` on the live origin. |
| Can users request that data be deleted? | **Yes** | Self-service: `DELETE /users/me` (`backend/src/routes/users.rs`), reachable from `/account-deletion` in the app. |

## Data types

Mapped from the ten categories the privacy policy declares. Every row is
collected; the "shared" column is discussed below the table.

| Play data type | What it is here | Policy |
| --- | --- | --- |
| Personal info → Email address, User IDs | Email, username, profile text, privacy settings | `data1` |
| Photos and videos → Photos | Profile avatar | `data1` |
| Messages → Other in-app messages | Sender, recipient, delivery and read timestamps, idempotency id, and message text under the condition above | `data9` |
| App activity → Other user-generated content | Reviews, lists, ratings, favourites, planned episodes | `data2` |
| App activity → App interactions | Library statuses, watch history and dates, follows, follow requests, notifications | `data2`, `data3` |
| App activity → Other actions | Region, language, TV Time import records | `data4` |
| App info and performance → Crash logs, Diagnostics | Sanitized error name, message, stack, app version, platform, fatality | `data6` |
| Device or other IDs | Expo push token, platform, app version, time-zone offset — only when release alerts are enabled | `data7` |
| Personal info → Other info | Public keys and fingerprint, plus two sealed copies of the private key, only when encryption is set up | `data10` |
| App activity → Other user-generated content | Blocked-account relationships, report reason and details, server-side snapshot of reported content | `data8` |

`data5` (session token hashes, IP address, user agent, request timestamps,
security and audit logs) is collected for authentication, fraud prevention and
security. Play exempts data used **solely** for those purposes from the
declaration. The owner-visible security timeline retains events for 90 days,
which is a retention decision, not a change of purpose — but whether the
exemption applies is a judgment call, and it is yours. Declaring it costs
nothing if unsure.

## Optional versus required

Several categories are collected only when the member turns something on, and
Play distinguishes this:

- Encryption key material — only after encryption setup (`data10`).
- Push token and platform — only when release alerts are enabled (`data7`).
- TV Time import records — only when the member supplies an import (`data4`).
- Avatar — only if one is uploaded (`data1`).

Everything else follows from using the account.

## Sharing

The policy names Cloudflare (edge), Resend (transactional email), Expo with
FCM/APNs (push delivery), and Google Drive (off-site backups, encrypted before
upload with the decryption key withheld).

Play distinguishes *sharing* — transfer to a third party acting for itself —
from transfer to a service provider processing on your behalf. On the facts,
each of these processes data to deliver a function you asked them to perform,
which normally makes them service providers rather than recipients. **That
characterisation is a judgment about your contracts with them, not something
the code can establish**, so confirm it rather than copying this paragraph.

No advertising identifier is collected and no data is sold. The single cookie
is a strictly necessary session cookie, not used for advertising or profiling.
